## 1. Introduction

A **block cipher** (like AES) only encrypts a single fixed-size block (e.g., 128 bits) at a time. A **mode of operation** defines how to repeatedly apply that block cipher to encrypt data of arbitrary length securely — and different modes have very different security properties, performance characteristics, and failure modes. Choosing the wrong mode is one of the most common real-world cryptography mistakes.

## 2. Why Modes Are Needed

If you simply split a message into blocks and encrypt each one independently with the same key, identical plaintext blocks produce identical ciphertext blocks — leaking patterns in the data. Modes of operation solve this by chaining blocks together or combining the cipher with a counter/IV so that identical plaintext blocks produce **different** ciphertext.

## 3. ECB (Electronic Codebook) — Insecure, Avoid

Each block is encrypted **independently** with the same key, with no chaining.

```
C1 = E(K, P1)
C2 = E(K, P2)
C3 = E(K, P3)
```

**Critical flaw:** identical plaintext blocks always produce identical ciphertext blocks, leaking structural patterns in the data. The famous "ECB penguin" image (an encrypted bitmap where the penguin outline remains clearly visible) demonstrates this vividly. **ECB should never be used for anything beyond a single block or non-sensitive data.**

## 4. CBC (Cipher Block Chaining)

Each plaintext block is **XORed with the previous ciphertext block** before encryption, chaining every block to all before it. The first block is XORed with a random **IV (Initialization Vector)**.

```
C1 = E(K, P1 XOR IV)
C2 = E(K, P2 XOR C1)
C3 = E(K, P3 XOR C2)
```

**Properties:** identical plaintext blocks produce different ciphertext (as long as prior blocks differ), sequential/not parallelizable for encryption (decryption CAN be parallelized), requires a unique, unpredictable IV per encryption.

**Known vulnerability:** susceptible to **padding oracle attacks** if the receiving system leaks information about padding validity errors (e.g., distinguishable error messages/timing) — see [[Cryptographic_Attacks]].

## 5. CFB (Cipher Feedback)

Turns a block cipher into a **self-synchronizing stream cipher**. The previous ciphertext block is encrypted and XORed with the current plaintext.

```
C1 = P1 XOR E(K, IV)
C2 = P2 XOR E(K, C1)
```

Useful for encrypting data in smaller units than the full block size (e.g., byte-by-byte streaming), but less common today compared to CTR/GCM.

## 6. OFB (Output Feedback)

Similar to CFB, but the **keystream** is generated by repeatedly encrypting the IV itself (rather than the ciphertext), then XORed with plaintext.

```
O1 = E(K, IV)
O2 = E(K, O1)
C1 = P1 XOR O1
C2 = P2 XOR O2
```

The keystream can be precomputed independent of the plaintext, but — like other stream-style modes — **reusing an IV with the same key is catastrophic**, exposing the XOR of two plaintexts.

## 7. CTR (Counter Mode)

Encrypts a **counter value** (nonce + incrementing counter) instead of the plaintext or previous ciphertext, then XORs the result with plaintext — turning the block cipher into a stream cipher.

```
Keystream_i = E(K, Nonce || Counter_i)
Ci = Pi XOR Keystream_i
```

**Advantages:** fully **parallelizable** for both encryption and decryption (each block is independent, only needs the counter value), no padding required, widely used in high-performance contexts. **Critical requirement:** the nonce+counter combination must **never repeat** for the same key — reuse catastrophically exposes plaintext via XOR of two messages.

## 8. GCM (Galois/Counter Mode) — Modern Standard

**GCM** combines **CTR mode encryption** with a built-in **Galois field-based authentication tag (GMAC)**, providing **AEAD** (Authenticated Encryption with Associated Data — see [[HMAC_and_MAC]]) in a single, efficient pass. This means GCM provides confidentiality AND integrity/authenticity simultaneously, without needing a separate MAC step.

**Why it's the modern default:** parallelizable like CTR, includes built-in tamper detection (an attacker modifying ciphertext causes tag verification to fail), and is the primary cipher suite used in TLS 1.2/1.3 (AES-GCM), IPSec, and SSH.

**Critical requirement:** like CTR, the nonce must **never repeat** for a given key — nonce reuse in GCM is especially catastrophic, potentially allowing full recovery of the authentication key and forgery of future messages.

## 9. Mode Comparison Table

| Mode | Parallelizable (Encrypt) | Requires Padding | Built-in Authentication | Status |
|---|---|---|---|---|
| ECB | Yes | Yes | No | **Insecure — avoid** |
| CBC | No (decrypt only) | Yes | No | Legacy but usable if implemented carefully (avoid padding oracle) |
| CFB | No | No | No | Legacy, uncommon |
| OFB | No (keystream precomputable) | No | No | Legacy, uncommon |
| CTR | Yes | No | No | Good, but needs separate MAC for authentication |
| GCM | Yes | No | Yes (built-in) | **Modern recommended default** |

## 10. Padding (PKCS#7)

Block ciphers in modes like CBC require plaintext to be an exact multiple of the block size. **PKCS#7 padding** adds bytes to fill the last block, where each padding byte's value equals the number of padding bytes added (e.g., 3 bytes needed → `03 03 03`). Modes like CTR and GCM avoid this entirely since they behave like stream ciphers.

## 11. Interview Questions

1. Why is ECB mode insecure? → **Identical plaintext blocks always produce identical ciphertext blocks, leaking data patterns**
2. What does CBC mode chain together? → **Each plaintext block is XORed with the previous ciphertext block before encryption**
3. What makes CTR mode parallelizable? → **Each block only depends on a counter value, not on previous ciphertext**
4. What does GCM provide that plain CTR mode doesn't? → **Built-in authentication/integrity (AEAD) via GMAC, alongside encryption**
5. What happens if you reuse a nonce in CTR or GCM mode? → **Catastrophic plaintext exposure (CTR) or potential key/authentication forgery (GCM)**
6. What attack is CBC mode particularly vulnerable to if implemented carelessly? → **Padding oracle attacks**

## 12. Key Points

- Block ciphers need a **mode of operation** to securely encrypt data longer than one block.
- **ECB is insecure** — never use it for real data (patterns leak).
- **CBC** chains blocks via XOR but is vulnerable to padding oracle attacks if mishandled.
- **CTR** turns a block cipher into a parallelizable stream cipher — fast, but no built-in authentication.
- **GCM** = CTR + built-in authentication (AEAD) — the modern recommended default (used in TLS 1.3).
- **Never reuse a nonce/IV** with the same key in CTR, GCM, CFB, or OFB modes.
